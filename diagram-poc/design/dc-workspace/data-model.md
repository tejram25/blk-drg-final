# DWS + Block Diagram — data model

One Oracle instance, **two schemas**, one owner per table.

```
                    ORACLE INSTANCE
   ┌──────────────────────┐   ┌──────────────────────┐
   │  DWS schema          │   │  BLK schema          │
   │  design              │   │  diagram             │
   │  design_artifact     │   │  diagram_content     │
   │  artifact_file       │   │  diagram_version     │
   │  artifact_kind       │   └──────────────────────┘
   │  artifact_publication│              ▲
   │  design_part_link    │              │ owns / writes
   │  design_member       │        BLK backend
   │  outbox_event        │
   └──────────────────────┘
              ▲
              │ owns / writes
        DWS backend
```

**The rule:** a service writes only its own schema. Anything it needs from the
other side it gets over REST, or through a versioned read-only view. There are
no cross-schema foreign keys — see [Why no cross-schema FK](#why-no-cross-schema-fk).

---

| Table | Owner (writes) | Other service |
|---|---|---|

| `DWS.artifact_publication` | DWS | — |
| `DWS.design_part_link` | DWS | — |
| `DWS.design_member` | DWS | — |
| `DWS.outbox_event` | DWS | Databricks reads |
| `BLK.diagram` | BLK | DWS reads `V_DIAGRAM_V1` |
| `BLK.diagram_content` | BLK | — |
| `BLK.diagram_version` | BLK | — |

## DWS schema

### design

The central object. One row per design; the Salesforce link lives here and
nowhere else (stakeholder point 2), at opportunity **header** level (point 7).

```sql
CREATE TABLE dws.design (
  id                NUMBER(19)        GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  public_id         VARCHAR2(40 CHAR) NOT NULL,   -- e.g. 'DSN-4788', shown in URLs
  name              VARCHAR2(200 CHAR) NOT NULL,
  -- What the user is designing, in their words: "48 V automotive BMS, 16 cells,
  -- ASIL-B, 10k/yr". For an ad-hoc design (no opportunity) this is the only
  -- statement of intent the agent has to work from.
  brief             VARCHAR2(4000 CHAR),
  customer          VARCHAR2(200 CHAR),
  region            VARCHAR2(8 CHAR),             -- eu | ap | ac
  stage             VARCHAR2(32 CHAR)  DEFAULT 'DRAFT' NOT NULL,
  -- The ONLY Salesforce data we store. No account/amount/close-date copies:
  -- the AI agent resolves the rest from Databricks by this id (point 3).
  -- Nullable by design: DWS supports standalone (ad-hoc) design sessions with
  -- no Opportunity. Confirmed by the stakeholder review.
  opportunity_id    VARCHAR2(18 CHAR),
  opportunity_linked_at TIMESTAMP(6),
  opportunity_linked_by VARCHAR2(320 CHAR),
  owner_email       VARCHAR2(320 CHAR) NOT NULL,
  created_at        TIMESTAMP(6) DEFAULT SYSTIMESTAMP NOT NULL,
  updated_at        TIMESTAMP(6) DEFAULT SYSTIMESTAMP NOT NULL,
  deleted_at        TIMESTAMP(6),                 -- soft delete
  CONSTRAINT uq_design_public   UNIQUE (public_id),
  CONSTRAINT ck_design_stage    CHECK (stage IN ('DRAFT','ACTIVE','WON','LOST','ARCHIVED')),
  CONSTRAINT ck_design_region   CHECK (region IN ('eu','ap','ac'))
);

-- "View Design" from Salesforce hits exactly this index.
CREATE INDEX ix_design_opp ON dws.design (opportunity_id);
CREATE INDEX ix_design_owner ON dws.design (owner_email);
```

One opportunity may have several designs — deliberately not unique.

### artifact_kind

Reference data, **not an enum in code**. Point 5 says the FAE workshop decides
what reaches the customer; making that a table means changing it is a config
change, not a release.

```sql
CREATE TABLE dws.artifact_kind (
  code              VARCHAR2(32 CHAR) PRIMARY KEY,
  label             VARCHAR2(80 CHAR) NOT NULL,
  -- Can an artifact of this kind EVER be shown in Salesforce?
  external_eligible CHAR(1) DEFAULT 'N' NOT NULL,
  sort_order        NUMBER(3) DEFAULT 100 NOT NULL,
  CONSTRAINT ck_kind_ext CHECK (external_eligible IN ('Y','N'))
);

INSERT INTO dws.artifact_kind VALUES ('BLOCK_DIAGRAM',   'Block diagram (source)', 'N', 10);
INSERT INTO dws.artifact_kind VALUES ('DIAGRAM_EXPORT',  'Block diagram (PDF/PNG)','Y', 20);
INSERT INTO dws.artifact_kind VALUES ('PRESENTATION',    'Presentation',           'Y', 30);
INSERT INTO dws.artifact_kind VALUES ('BOM',             'Bill of materials',      'Y', 40);
INSERT INTO dws.artifact_kind VALUES ('DATASHEET',       'Datasheet',              'Y', 50);
INSERT INTO dws.artifact_kind VALUES ('REFERENCE_DESIGN','Reference design',       'Y', 60);
INSERT INTO dws.artifact_kind VALUES ('SKETCH',          'Sketch',                 'N', 70);
INSERT INTO dws.artifact_kind VALUES ('NOTE',            'FAE note',               'N', 80);
INSERT INTO dws.artifact_kind VALUES ('RECOMMENDATION',  'AI recommendation',      'N', 90);
```

`BLOCK_DIAGRAM` (the JSON) is `'N'`; `DIAGRAM_EXPORT` (the PDF) is `'Y'` —
exactly point 5. FAE notes are `'N'`.

### design_artifact

The registry. Categories for the DWS UI (point 6) and the publish state machine
for Salesforce (point 5).

```sql
CREATE TABLE dws.design_artifact (
  id              NUMBER(19) GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  design_id       NUMBER(19)        NOT NULL,
  kind            VARCHAR2(32 CHAR) NOT NULL,
  name            VARCHAR2(255 CHAR) NOT NULL,
  status          VARCHAR2(16 CHAR) DEFAULT 'DRAFT' NOT NULL,
  -- Only meaningful once published; the trigger below stops it being set on a
  -- kind that is not externally eligible.
  external_visible CHAR(1) DEFAULT 'N' NOT NULL,
  current_file_id NUMBER(19),                     -- newest bytes
  -- Soft reference to BLK.diagram.id for artifacts generated from a diagram.
  -- No FK: different owner, different schema.
  source_diagram_id NUMBER(19),
  created_by      VARCHAR2(320 CHAR) NOT NULL,
  created_at      TIMESTAMP(6) DEFAULT SYSTIMESTAMP NOT NULL,
  updated_at      TIMESTAMP(6) DEFAULT SYSTIMESTAMP NOT NULL,
  deleted_at      TIMESTAMP(6),
  CONSTRAINT fk_artifact_design FOREIGN KEY (design_id) REFERENCES dws.design (id),
  CONSTRAINT fk_artifact_kind   FOREIGN KEY (kind)      REFERENCES dws.artifact_kind (code),
  CONSTRAINT ck_artifact_status CHECK (status IN ('DRAFT','IN_REVIEW','PUBLISHED','ARCHIVED')),
  CONSTRAINT ck_artifact_ext    CHECK (external_visible IN ('Y','N')),
  -- Belt and braces: cannot be externally visible unless published.
  CONSTRAINT ck_artifact_ext_pub CHECK (external_visible = 'N' OR status = 'PUBLISHED')
);

CREATE INDEX ix_artifact_design ON dws.design_artifact (design_id, kind);
CREATE INDEX ix_artifact_pub    ON dws.design_artifact (design_id, status, external_visible);
```

The database enforces "external implies published". The kind rule needs a
trigger because it spans tables:

```sql
CREATE OR REPLACE TRIGGER dws.trg_artifact_external
BEFORE INSERT OR UPDATE OF external_visible, kind ON dws.design_artifact
FOR EACH ROW WHEN (NEW.external_visible = 'Y')
DECLARE v_ok CHAR(1);
BEGIN
  SELECT external_eligible INTO v_ok FROM dws.artifact_kind WHERE code = :NEW.kind;
  IF v_ok <> 'Y' THEN
    RAISE_APPLICATION_ERROR(-20001,
      'Artifact kind ' || :NEW.kind || ' may not be exposed externally');
  END IF;
END;
```

That is the guardrail from Story 2 — even a bad INSERT cannot leak a source
diagram or an FAE note to a customer.

### artifact_file

Metadata, versioned. Separate from the artifact so re-exporting a diagram adds a
version instead of overwriting history. The **bytes are not here** — they live
in object storage, addressed by `storage_key` (open question 7, resolved in
[artifact-storage.md](./artifact-storage.md)).

```sql
CREATE TABLE dws.artifact_file (
  id            NUMBER(19) GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  artifact_id   NUMBER(19)         NOT NULL,
  version_no    NUMBER(5)          NOT NULL,
  file_name     VARCHAR2(255 CHAR) NOT NULL,
  content_type  VARCHAR2(120 CHAR) NOT NULL,
  size_bytes    NUMBER(19)         NOT NULL,
  sha256        VARCHAR2(64 CHAR)  NOT NULL,   -- integrity, dedupe, AND the storage address
  storage_key   VARCHAR2(512 CHAR) NOT NULL,   -- object-store key, derived from sha256
  store_region  VARCHAR2(16 CHAR),             -- which regional bucket (data residency)
  source_url    VARCHAR2(1024 CHAR),           -- when fetched (e.g. a datasheet)
  created_by    VARCHAR2(320 CHAR) NOT NULL,
  created_at    TIMESTAMP(6) DEFAULT SYSTIMESTAMP NOT NULL,
  CONSTRAINT fk_file_artifact FOREIGN KEY (artifact_id) REFERENCES dws.design_artifact (id),
  CONSTRAINT uq_file_version  UNIQUE (artifact_id, version_no)
);
```

`size_bytes` and `sha256` are written by the one service that also stores the
bytes — that is what stops the Story 3 drift, and it is what lets the list
endpoint report a size without touching the store. There is no `bytes` column:
the store holds them, and the metadata row is written **only after** the bytes
are safely stored, so a row can never point at content that is not there
([artifact-storage.md](./artifact-storage.md) § Write path).

### artifact_publication

Who approved what, and when. Point 5 is a governance requirement, so it needs an
audit trail, not just a status column.

```sql
CREATE TABLE dws.artifact_publication (
  id            NUMBER(19) GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  artifact_id   NUMBER(19)        NOT NULL,
  file_id       NUMBER(19)        NOT NULL,   -- exact version approved
  action        VARCHAR2(16 CHAR) NOT NULL,   -- PUBLISH | UNPUBLISH
  actor_email   VARCHAR2(320 CHAR) NOT NULL,
  reason        VARCHAR2(500 CHAR),
  created_at    TIMESTAMP(6) DEFAULT SYSTIMESTAMP NOT NULL,
  CONSTRAINT fk_pub_artifact FOREIGN KEY (artifact_id) REFERENCES dws.design_artifact (id),
  CONSTRAINT fk_pub_file     FOREIGN KEY (file_id)     REFERENCES dws.artifact_file (id),
  CONSTRAINT ck_pub_action   CHECK (action IN ('PUBLISH','UNPUBLISH'))
);
```

Recording `file_id` matters: "the customer approved *that* PDF", not "that
artifact, whatever it contains today".

### design_part_link

Evolution of today's `project_part_links`, re-keyed to `design`.

```sql
CREATE TABLE dws.design_part_link (
  id            NUMBER(19) GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  design_id     NUMBER(19)         NOT NULL,
  part_id       VARCHAR2(64 CHAR)  NOT NULL,
  part_number   VARCHAR2(128 CHAR) NOT NULL,
  manufacturer  VARCHAR2(200 CHAR),
  description   VARCHAR2(1024 CHAR),
  region        VARCHAR2(8 CHAR),              -- which catalogue answered
  status        VARCHAR2(40 CHAR),             -- lifecycle at link time
  unit_price    VARCHAR2(40 CHAR),
  currency      VARCHAR2(8 CHAR),
  quantity      NUMBER(9) DEFAULT 1 NOT NULL,
  linked_by     VARCHAR2(320 CHAR) NOT NULL,
  linked_at     TIMESTAMP(6) DEFAULT SYSTIMESTAMP NOT NULL,
  CONSTRAINT fk_partlink_design FOREIGN KEY (design_id) REFERENCES dws.design (id),
  CONSTRAINT uq_partlink        UNIQUE (design_id, part_id)
);
```

The unique constraint is what makes linking idempotent.

### design_member

Access control. Needed for the entitlement gap in point 3 — the AI agent must
not resolve opportunity context for a design the caller cannot see.

```sql
CREATE TABLE dws.design_member (
  design_id   NUMBER(19)         NOT NULL,
  user_email  VARCHAR2(320 CHAR) NOT NULL,
  role        VARCHAR2(16 CHAR)  NOT NULL,
  added_at    TIMESTAMP(6) DEFAULT SYSTIMESTAMP NOT NULL,
  CONSTRAINT pk_design_member PRIMARY KEY (design_id, user_email),
  CONSTRAINT fk_member_design FOREIGN KEY (design_id) REFERENCES dws.design (id),
  CONSTRAINT ck_member_role   CHECK (role IN ('OWNER','EDITOR','APPROVER','VIEWER'))
);
```

`APPROVER` is the role the publish endpoint checks.

### outbox_event

Feeds Databricks (points 3 and 4) without a nightly full scan and without
Databricks reading the tables directly.

```sql
CREATE TABLE dws.outbox_event (
  id            NUMBER(19) GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  aggregate     VARCHAR2(32 CHAR) NOT NULL,   -- DESIGN | ARTIFACT | PART_LINK
  aggregate_id  NUMBER(19)        NOT NULL,
  event_type    VARCHAR2(40 CHAR) NOT NULL,   -- CREATED | UPDATED | PUBLISHED …
  -- Metadata ONLY — never diagram JSON, canvas objects or artifact bytes.
  -- Databricks holds the linkage, design metadata and derived semantics; the
  -- artifacts themselves stay here. Serialising a whole design into this column
  -- would rebuild the artifact store the review explicitly rejected.
  payload       CLOB              NOT NULL,
  occurred_at   TIMESTAMP(6) DEFAULT SYSTIMESTAMP NOT NULL,
  published_at  TIMESTAMP(6)                  -- NULL = not yet shipped
);

CREATE INDEX ix_outbox_unpub ON dws.outbox_event (published_at, id);
```

Written in the same transaction as the change, so the feed cannot miss an event.

What Databricks receives, per the review: the opportunity ↔ design linkage,
design metadata, AI-generated summaries and tags, and semantic information for
finding similar designs. Not artifacts, not versions, not attachments — so a
design revision never has to be synchronised anywhere.

Databricks holds a **copy** of the linkage for analytics. `dws.design` remains
the system of record; nothing writes the linkage in Databricks.

## The three views

Cross-service reads go through versioned views, never base tables. The `_V1`
suffix lets the owner change the table underneath and keep the promise.

```sql
-- BLK needs a design's name/state to render its header.
CREATE OR REPLACE VIEW dws.v_design_v1 AS
SELECT id AS design_id, public_id, name, region, stage, opportunity_id, owner_email
FROM   dws.design
WHERE  deleted_at IS NULL;

GRANT SELECT ON dws.v_design_v1 TO blk_reader;

-- DWS lists a design's diagrams without knowing BLK's storage.
CREATE OR REPLACE VIEW blk.v_diagram_v1 AS
SELECT id AS diagram_id, design_id, name, classification, owner_email, updated_at
FROM   blk.diagram
WHERE  deleted_at IS NULL;

GRANT SELECT ON blk.v_diagram_v1 TO dws_reader;

-- What Salesforce is allowed to see. The ONLY thing the SFDC-facing endpoint
-- reads — it cannot accidentally return a draft or an internal artifact.
CREATE OR REPLACE VIEW dws.v_published_artifact_v1 AS
SELECT a.id AS artifact_id, d.opportunity_id, d.public_id AS design_public_id,
       d.name AS design_name, a.kind, k.label AS kind_label, a.name,
       f.file_name, f.content_type, f.size_bytes, a.updated_at
FROM   dws.design_artifact a
JOIN   dws.design         d ON d.id = a.design_id
JOIN   dws.artifact_kind  k ON k.code = a.kind
JOIN   dws.artifact_file  f ON f.id = a.current_file_id
WHERE  a.status = 'PUBLISHED'
AND    a.external_visible = 'Y'
AND    k.external_eligible = 'Y'
AND    a.deleted_at IS NULL
AND    d.deleted_at IS NULL;
```

Three independent conditions have to hold before anything reaches a customer.

## Grants

```sql
-- Each service owns its schema and can read only the other's published views.
GRANT CONNECT, RESOURCE TO dws_app;
GRANT CONNECT, RESOURCE TO blk_app;

GRANT SELECT ON blk.v_diagram_v1 TO dws_app;
GRANT SELECT ON dws.v_design_v1  TO blk_app;
-- Deliberately absent: any INSERT/UPDATE/DELETE across the boundary.
```

That last line is the whole design, expressed as a permission. Story 2's rogue
INSERT fails with `ORA-01031: insufficient privileges` rather than reaching a
customer.

## Why no cross-schema FK

A foreign key from `BLK.diagram.design_id` to `DWS.design.id` is possible within
one instance, and tempting. Skip it:

- It re-couples deploys — DWS can no longer alter or partition `design` without
  BLK's constraint objecting.
- It forces a lock order across two services' transactions; that is a deadlock
  waiting for a busy afternoon.
- It cannot survive the two schemas ever moving to separate databases.

Instead: BLK stores `design_id` as a plain number, validated at write time by
calling DWS. A nightly reconciliation job reports orphans. Slightly weaker
guarantee, far weaker coupling — the right trade for a service boundary.

## Where the writes happen

```
FAE exports a block diagram to PDF
  BLK  renders the PDF
  BLK  POST https://dws.arrow.com/api/designs/42/artifacts
         { kind: "DIAGRAM_EXPORT", name: "Power stage v3",
           sourceDiagramId: 118, contentType: "application/pdf" }
  DWS  writes design_artifact (status DRAFT, external_visible N)
       writes artifact_file  (bytes, size, sha256)
       writes outbox_event   (ARTIFACT/CREATED)

FAE manager publishes it
  DWS  POST /api/artifacts/900/publish
       checks design_member.role = APPROVER
       sets status PUBLISHED, external_visible Y   (trigger checks kind)
       writes artifact_publication + outbox_event

Salesforce "View Design"
  SFDC GET /api/sfdc/opportunities/0064x.../designs        → design (all linked)
  SFDC GET /api/sfdc/designs/DSN-4788/artifacts            → v_published_artifact_v1
  SFDC GET /api/sfdc/artifacts/900/content                 → streams the file
```

Three calls, each only on a click — stakeholder points 1 and 2.

Note the first call is **not** artifact-filtered: point 2 says list every design
linked to the opportunity. The filter applies one level down, to the artifacts
inside a design. A design with nothing published still appears, just empty.

## Two surfaces, one application

DWS renders two different views of the same design, and the difference is a
security boundary rather than a display preference.

| | SFDC-embedded | DWS workspace |
|---|---|---|
| Audience | Sales rep, inside the opportunity | FAE, doing the design work |
| Artifacts | Published **and** externally eligible only | Everything — drafts, notes, sketches, diagram JSON |
| Block diagram | PNG/PDF preview and download | Opens the BLK editor, editable |
| Actions | Download | Create, edit, upload, publish |
| Route | `/embed/opportunity/{oppId}` | `/designs/{publicId}` |
| API namespace | `/api/sfdc/**` | `/api/**` |

```
SALESFORCE (sales rep)                    DWS WORKSPACE (FAE, own tab)
┌────────────────────────────┐            ┌────────────────────────────┐
│ Opportunity 0064x…         │            │ Design DSN-4788            │
│ [View Design]              │            │                            │
│   ↓                        │            │ Block diagrams   ▸ 3       │
│ ┌── iframe: DWS embed ───┐ │            │ Presentations    ▸ 1       │
│ │ Designs (3)            │ │            │ Notes            ▸ 5  ←────┼─ drafts,
│ │  DSN-4788 ▸            │ │            │ Sketches         ▸ 2       │  internal,
│ │   ├ [PNG] Power stage  │ │            │ Recommendations  ▸ 4       │  everything
│ │   ├ [PDF] Proposal     │ │            │                            │
│ │   └ [CSV] BOM          │ │            │ click a diagram →          │
│ │                        │ │            │  ┌── iframe: BLK ────────┐ │
│ │ published only         │ │            │  │  editable canvas      │ │
│ └────────────────────────┘ │            │  └───────────────────────┘ │
└────────────────────────────┘            └────────────────────────────┘
```

**Clicking a diagram in Salesforce previews or downloads the image. It does not
open the editor** — the JSON is exactly what point 5 keeps internal.

### The filter is server-side, not a UI flag

The embedded view reads `v_published_artifact_v1` and nothing else. It is
physically unable to return a draft, whatever the frontend asks for.

If "embedded mode" were a flag that hid drafts in the template, anyone could
open devtools and call the full endpoint. Hence the separate namespace: the
`/api/sfdc/**` handlers never touch `design_artifact` directly.

### Editing from Salesforce: a link, not a mode

An FAE viewing the opportunity will want to jump in and edit. Rather than making
the embedded view do double duty, it carries an **Open in Design Workspace**
link that opens DWS at top level, in a new tab:

```
https://dws.arrow.com/designs/DSN-4788
```

Three things follow, all of them simplifications:

- the embedded view stays small and provably read-only;
- editing happens outside the iframe, so the framed-session problems
  (third-party cookies, an IdP that refuses to render in a frame) never apply to
  the editing path;
- access control needs no special case — the link works for a `design_member`
  and shows an ordinary login for anyone else.

## Migration from what exists today

| Today | Becomes |
|---|---|
| `diagrams` | `BLK.diagram` + `BLK.diagram_content` (split the CLOB) |
| `diagram_versions` | `BLK.diagram_version` (+ `version_no`) |
| `project_files` | `DWS.design_artifact` + `DWS.artifact_file` |
| `project_part_links` | `DWS.design_part_link` (re-key `project_id` → `design_id`) |
| `ProjectSummary.opportunity` | `DWS.design.opportunity_id` |
| — (new) | `artifact_kind`, `artifact_publication`, `design_member`, `outbox_event` |

Projects today are string ids (`PRJ-4788`) with no table; `design.public_id`
keeps that shape so existing URLs survive.

## Open questions for the review

1. ~~**Bytes in Oracle, or object storage?**~~ **Resolved: object storage.**
   `artifact_file` now carries only `storage_key`; the `bytes BLOB` is gone.
   See [artifact-storage.md](./artifact-storage.md).
2. **Who is `APPROVER`?** Point 5 needs a named role. Is it the design owner's
   manager, a regional FAE lead, or anyone with the Salesforce role?
3. **Un-publishing.** If an artifact is withdrawn after a customer has seen it,
   does Salesforce show a tombstone or does it silently vanish?
4. **Diagram deletion** with published exports referencing it — block, or leave
   the export orphaned but intact? (The soft reference allows the latter.)
5. **One design, many opportunities?** The model says no. Confirm a reference
   design reused across opportunities is a *copy*, not a shared row.
6. **Does an FAE ever need to edit from inside Salesforce**, or is "Open in
   Design Workspace" in a new tab acceptable? A new tab removes a meaningful
   amount of integration risk — it keeps every editing path out of the iframe —
   so this is worth settling early rather than discovering late.
